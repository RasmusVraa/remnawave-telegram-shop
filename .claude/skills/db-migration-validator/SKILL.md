# Валидатор БД-миграций

Миграция, которая сломала данные на продакшене, откатывается сложно и медленно.
Проверка перед коммитом — самая дешёвая страховка.

## Контекст проекта

- PostgreSQL, миграции golang-migrate в `db/migrations/`: пары
  `0000NN_имя.up.sql` / `0000NN_имя.down.sql`, номера подряд.
- Применяются при старте бота (`database.RunMigrations`) через драйвер
  `pgx/v5` отдельным коротким пулом **без** `statement_timeout`. Основной пул
  приложения живёт с `statement_timeout=30s`.
- Бот обновляют поверх живой базы, иногда откатывают образ без отката БД:
  старая версия должна пережить новую схему.

## Когда применять

- Любая новая миграция в `db/migrations/`.
- Перед git push, если в коммитах есть `*.sql` в папке миграций.

## Порядок проверки

### 1. Нумерация и пара файлов

```bash
ls db/migrations | tail -6
```

- Номер следующий после последнего, нет дублей номера.
- Есть и `.up.sql`, и `.down.sql`; `down` действительно отменяет `up`.

### 2. Применить на одноразовой базе

```bash
docker run -d --name mig-pg -e POSTGRES_PASSWORD=t -p 127.0.0.1:55432:5432 postgres:17
CABINET_INTEGRATION_PG='postgres://postgres:t@127.0.0.1:55432/postgres?sslmode=disable' \
  go test -tags=integration -count=1 -run TestHotIndexes ./internal/database/
docker rm -f -v mig-pg
```

Любой интеграционный тест накатывает все миграции до последней — упавшая
миграция видна сразу. Для проверки `down` — `migrate -path db/migrations
-database "$URL" down 1` и снова `up`.

### 3. Потеря и переписывание данных

- **DROP TABLE / DROP COLUMN** — намеренно? Старая версия бота после отката
  образа обратится к удалённой колонке и упадёт. Сначала выпуск, который
  перестаёт её читать, удаление — следующим.
- **DELETE / UPDATE без WHERE** — переписывает все строки.
- **ON DELETE CASCADE** на новых FK — удаление клиента не должно молча уносить
  покупки и платёжную историю, если это не задумано.
- **NOT NULL без DEFAULT** на существующей таблице — упадёт на непустой базе.

### 4. Блокировки на больших таблицах

`purchase`, `customer`, `referral` у живых магазинов — сотни тысяч строк.

- **Индекс** — `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, и **одна команда на
  файл**: несколько команд golang-migrate отправляет одним multi-statement
  запросом, то есть неявной транзакцией, а CONCURRENTLY в транзакции запрещён.
  Образцы — `000049`…`000053`. В `down` — `DROP INDEX CONCURRENTLY IF EXISTS`.
- **ALTER TABLE ... ADD COLUMN** с константным DEFAULT в PostgreSQL 11+
  мгновенный; с volatile DEFAULT (`now()`, функция) — переписывает таблицу.
- **ADD CONSTRAINT / UNIQUE** на большой таблице — сначала проверить дубли в
  данных; для FK — `NOT VALID` + отдельный `VALIDATE CONSTRAINT`.
- Бэкфилл данных — пачками, а не одним UPDATE на всю таблицу.

### 5. Совместимость с кодом

- Колонки совпадают с тем, что читает/пишет `internal/database/*.go`
  (явные списки колонок в `sq.Select`/`Insert`).
- Новая колонка в whitelist `UpdateFields`, если её пишут динамически.
- `IF NOT EXISTS` / `IF EXISTS` там, где миграцию могли частично применить.

### 6. Контрольный список

- [ ] Номер подряд, есть `.up.sql` и `.down.sql`
- [ ] Миграция накатывается на чистую базу и на базу с данными
- [ ] Нет случайных DROP/DELETE/UPDATE без WHERE
- [ ] Индексы — CONCURRENTLY, по одному на файл
- [ ] Старая версия бота переживает новую схему (откат образа без отката БД)
- [ ] Комментарий в миграции объясняет «зачем»
