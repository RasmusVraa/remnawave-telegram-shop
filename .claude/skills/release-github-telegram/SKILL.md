# Заметки к релизу: GitHub + Telegram

## Роль

По `git log`, диффу и контексту чата готовишь **два варианта** одного релиза:

1. **GitHub** — **GitHub Flavored Markdown** (поле *Release notes* на GitHub: `##`, списки, `**жирный**`, ссылки `[текст](url)`).
2. **Telegram** — в `RELEASE_NOTES.md` хранится **plain-исходник** (без HTML/Markdown-разметки). При публикации `tools/release` сам собирает HTML: версия — кликабельная ссылка на GitHub Release, заголовки секций — `<b>`, в конце — кликабельный футер из `.env.release`.

Смысл обоих вариантов совпадает; **не смешивай** GFM и «телеграм-исходник» в одном блоке.

## Куда писать (обязательно)

- Файл **`RELEASE_NOTES.md`** в корне воркспейса.
- При каждой генерации **полностью перезаписывай** файл; старое не дописывай.
- В чат — короткое резюме и вопрос об утверждении; полный текст — в `RELEASE_NOTES.md`.

## Структура `RELEASE_NOTES.md`

Два верхних раздела, порядок фиксированный:

```markdown
# Релиз X.Y.Z

## Вариант для GitHub Releases

…только GFM…

---

## Вариант для Telegram

…plain-исходник по правилам ниже…
```

Между блоками — строка из трёх дефисов `---` на отдельной строке.

**Теги и URL без префикса `v`:** в этом репо всегда `4.12.2` / `…/releases/tag/4.12.2`, никогда `v4.12.2`. То же в первой строке Telegram-блока. `tools/release` срежет ведущий `v`, если он всё же попал в файл.

### GitHub (GFM)

Заголовки секций **строго** (с `## `):

| Смысл | Заголовок |
|--------|-----------|
| Новые фичи | `## 🚀 Новое` |
| Улучшения без новых фич | `## ✨ Улучшения` |
| Багфиксы | `## 🐛 Исправления` |
| Внутренности / deps | `## 🧱 Технические изменения` — **обычно не нужна**, см. «Стиль» |
| Что сделать при обновлении | `## ⚠️ При обновлении` — только если есть обязательные шаги |

Порядок: **🚀 Новое** → **✨ Улучшения** → **🐛 Исправления** → (редко) **🧱 Технические изменения**. Опционально: `## ⚠️ Breaking changes` / `## ⚠️ При обновлении` в конце, перед или вместо «Технических».

Списки `- `, жирный `**…**`, ссылки GFM. Весь блок GitHub **не** оборачивай в fenced code.

**Никаких цитат (`>`), `<blockquote>` и `<details>`** — сворачивание секций
существует только в телеграм-посте (см. «Свёрнутые цитаты»). В GitHub все
пункты видны сразу, независимо от их количества.

### Telegram (plain-исходник в файле)

В файле **никакой** разметки HTML/Markdown: не используй `##`, `**`, `` ` ``, `<b>`, `<a>`, `[текст](url)`.

**Первая строка** — версия и URL релиза на GitHub через пробел:

```text
4.12.1 https://github.com/MrMe0ws/remnawave-telegram-shop/releases/tag/4.12.1
```

Допустимо также: `4.12.1 (https://github.com/...)`. Репозиторий по умолчанию: `MrMe0ws/remnawave-telegram-shop`.

**Заголовки секций** — строка без `##`:

- `🚀 Новое`
- `✨ Улучшения`
- `🐛 Исправления`
- `🧱 Технические изменения` — обычно не писать
- опционально: `⚠️ Breaking changes` / `⚠️ При обновлении`

**Пустые строки (обязательно для Telegram):**
- между **пунктами** одной секции — **одна пустая строка**;
- между **секциями** — **две** пустые строки;
- между заголовком секции и первым `•` — **одна** пустая строка;
- первая строка (версия + URL) отделена от первой секции **одной** пустой строкой.

Пример фрагмента Telegram-блока:

```text
🚀 Новое

• Первый пункт длинный текст…

• Второй пункт длинный текст…


⚠️ При обновлении

• Обновите образ бота до 4.12.6 — схема БД обновится сама при старте.

• Чтобы включить фичу, задайте нужные URL в .env.
```

В исходнике `RELEASE_NOTES.md` соблюдай те же отступы. `tools/release` при сборке HTML **сам** выставляет: пустая строка после заголовка/между пунктами и две пустые между секциями — даже если в файле забудут.

**Не** добавляй в файл футер «Meows VPN Group» — его дописывает `tools/release` из `.env.release`.

Порядок секций тот же, что в GitHub. Пустые секции не выводи.

### Как уйдёт в Telegram (HTML, делает CLI)

Пример результата отправки (`parse_mode=HTML`):

- `4.12.1` — ссылка на GitHub Release
- `✨ Улучшения` / другие заголовки — жирный
- после заголовка секции — пустая строка, затем `• …`; между пунктами — пустая строка; между секциями — две пустые
- в конце: optional custom emoji (`RELEASE_TG_FOOTER_CUSTOM_EMOJI_ID`) + `Meows VPN Group` — ссылка на `https://t.me/meows_vpn_bot`

**GitHub (GFM):** между `- ` пунктами пустые строки **не** ставь — иначе Markdown разобьёт список.

### Лимит Telegram: 4096 символов (жёсткий)

Telegram Bot API не принимает сообщение длиннее **4096 символов**. Считаются
символы текста, а не разметка: `<b>`, `<a href>` и `<blockquote>` в лимит не
входят, зато входят все эмодзи и пункты. `tools/release` проверяет длину перед
отправкой и падает с понятной ошибкой:

```text
telegram message is 5454 runes (limit 4096); shorten Telegram section in RELEASE_NOTES.md
```

Практика: **держи телеграм-блок в пределах ~3800 символов**, оставляя запас на
футер, который дописывает CLI. GitHub-вариант в лимит не упирается — сокращать
нужно только телеграм-блок, и это нормально: варианты не обязаны совпадать по
длине, только по смыслу.

Как сокращать, если не влезло:
- убрать вводные обороты и повторы, оставить «что изменилось + что это даёт»;
- склеить однотипные мелкие пункты в один («синеватая рамка и смешение цветов
  на кнопках»);
- вынести детали в GitHub-вариант, в Telegram оставить одну фразу.

Сворачивание секций в цитату длину **не уменьшает** — это только про вид.

### Свёрнутые цитаты — ТОЛЬКО в Telegram (делает CLI сам)

**В GitHub-варианте цитат и сворачивания нет вообще.** Там обычные GFM-списки
`- `: GitHub не умеет раскрывающиеся цитаты, а `<details>` в релизноты не
вставляем. Всё, что описано ниже, относится исключительно к телеграм-посту.

В телеграм-посте `tools/release` оборачивает пункты секции в
`<blockquote expandable>` — раскрывающуюся цитату Telegram, — когда в секции
**больше двух пунктов** и это одна из второстепенных секций:

- `✨ Улучшения`
- `🐛 Исправления`
- `⚠️ При обновлении`
- `🧱 Технические изменения`
- `⚠️ Breaking changes`

`🚀 Новое` не сворачивается никогда: это то, ради чего пост читают.

В `RELEASE_NOTES.md` **ничего для этого делать не нужно** — пиши обычные пункты
с `•`, разметку добавит CLI (`collapsibleSection` в `tools/release/notes.go`,
порог — `collapsibleMinItems`). Не вставляй `<blockquote>` в файл руками.

Технически разделение гарантировано устройством CLI: сворачивание живёт внутри
`FormatTelegramHTML`, а в GitHub Release уходит `notes.GitHubBody` — сырой блок
из файла, мимо форматтера. Проверено тестом `TestGitHubBodyHasNoTelegramMarkup`.

Что из этого следует для текста: первый пункт свёрнутой секции виден в превью
целиком, остальные скрыты. Поэтому **самый важный пункт секции ставь первым** —
он и будет тем, что человек прочитает, не разворачивая.

## Источник правды

1. `git log` / при необходимости `git show`, узкий `git diff`.
2. Контекст чата.
3. Конфликт — приоритет репозиторию.

## Стиль (аудитория — простой пользователь)

Changelog читают владельцы бота/кабинета, не разработчики. Цель — **суть обновления и польза**, без воды.

**Пиши:**
- что изменилось для пользователя / админа и **что это даёт** (проще поставить, удобнее в кабинете, починили оплату…);
- коротко, по-человечески, без жаргона.

**Не пиши** (в changelog обычно лишнее):
- имена файлов, пакетов, функций, CSS-переменных, миграций, commit hash;
- «через docker inspect», «force-recreate», внутренние флаги, стек, рефакторинг «под капотом» без видимого эффекта;
- секцию **🧱 Технические изменения** — по умолчанию **пропускай**. Добавляй только если пользователь явно просит техдетали.

**В конце — только если критично что-то сделать** (иначе секцию не добавляй):

GitHub: `## ⚠️ При обновлении`  
Telegram: строка `⚠️ При обновлении`, ниже пункты с `•` (с пустыми строками между пунктами).

Примеры действий без воды:
- обновить образ бота до этой версии;
- подтянуть новые тексты в `translations/` (или пересобрать/перезалить переводы) — только если деплой не из образа / volume;
- сделать бэкап БД перед крупным обновлением (редко);
- добавить новые переменные в `.env` (назвать коротко, без лекции).

### Миграции БД (важно — не путать админов)

В этом проекте миграции **не делаются руками**.

Факт:
- SQL из `db/migrations` **лежат в Docker-образе** (`COPY … /db` в Dockerfile);
- при старте бота `RunMigrations` накатывает новые версии **сам**.

В changelog / «При обновлении»:
- **Не пиши:** «примените миграции», «запустите migrate», «убедитесь, что файл миграции N есть в папке на сервере».
- **Пиши** (если схема менялась): одной фразой к обновлению образа, например: «Обновите образ бота до X.Y.Z — схема БД обновится сама при старте.»
- Отдельный пункт только про миграции — обычно **не нужен**, если уже есть пункт про обновление образа.
- Номера файлов миграций (`000040_…`) в пользовательский changelog **не** выноси.

Классификация секций: Новое / Улучшения / Исправления — как в таблице GitHub. Технические — редко.

### Как найти точку отсчёта (всегда, до чтения `git log`)

```bash
git fetch --tags origin                              # свежий тег мог быть создан не здесь
git tag --list '[0-9]*' --sort=-v:refname | head -5  # только релизные теги
git log --oneline <последний_тег>..HEAD
```

Три ловушки, каждая уже давала неверный changelog:

1. **Без `git fetch --tags` последнего релиза в клоне может не быть.**
   `tools/release` создаёт тег через `gh`, то есть на стороне GitHub; локально
   он появляется только после fetch. Диапазон тогда молча берётся от
   позапрошлого релиза, и в заметки попадает чужой, уже вышедший релиз целиком.
2. **`git tag --sort=-v:refname | head -1` в этом репозитории врёт:** namespace
   смешанный (`5.3.0`, `v4.4.1`, `upstream-4.1.1`, `3.5.3`), и `v4.4.1`
   сортируется выше `5.3.0`. Отсюда фильтр `--list '[0-9]*'`.
3. **Не выбирай тег глазами из списка.** «Самый свежий на вид» — не то же
   самое, что предыдущий релиз.

Проверка перед написанием текста: `git log -1 --format='%h %ci %s' <тег>`.
Коммит тега должен быть вершиной `main` на момент, когда ветка отошла от неё.
Если это не так — диапазон выбран неверно, и часть пунктов уже вышла.

Номер нового релиза считается от найденного тега: есть новые фичи — минорный
шаг (`5.3.0` → `5.4.0`), только исправления — патч.

### Точка отсчёта — предыдущий РЕЛИЗ, а не начало разработки

Это правило нарушается чаще всего и портит changelog сильнее прочего.

**«Улучшения» и «Исправления» описывают разницу с предыдущей released-версией.**
Читатель сидит на 5.1.0. Если баг возник и был починен внутри цикла 5.2.0, у
читателя этого бага **никогда не было** — пункт про починку он не поймёт и
решит, что пропустил что-то важное.

Проверка перед каждым пунктом «Улучшений» и «Исправлений»: **существовало ли
это в предыдущем релизном теге?** Если нет — пункт не нужен.

| Ситуация | Куда |
|----------|------|
| Фича новая целиком | `🚀 Новое` — одним пунктом, включая её внутреннее устройство |
| Баг был в предыдущем релизе, починен сейчас | `🐛 Исправления` |
| Баг появился и умер внутри текущего цикла | **никуда** |
| Доводка новой фичи (правки UI, рефакторинг по ходу) | **никуда** — фича описывается сразу в готовом виде |
| Улучшение того, что было в предыдущем релизе | `✨ Улучшения` |

Примеры (цикл 5.3.0, предыдущий релиз 5.2.0):

- Раздел «Платежи» — новый. Правки его модалки по ходу разработки **не пункт
  «Улучшений»**: до 5.3.0 модалки не было вовсе. Всё это — часть одного пункта
  в «Новом».
- «Бот уходил в цикл перезапуска» — регрессия, внесённая и починенная внутри
  цикла. В changelog **не идёт**: на 5.2.0 её не было.
- «Модалки админки стали непрозрачными» — **идёт в «Улучшения»**: полупрозрачный
  фон был и в 5.2.0, читатель его видит прямо сейчас.

Практический приём: сомневаешься — посмотри `git show <прошлый_тег>:<файл>` и
проверь, что было в релизе. Дешевле, чем гадать.

Не путать с ценностью для читателя: внутренняя доводка может быть большой
работой, но changelog — не отчёт о проделанном, а ответ на вопрос «что мне даст
обновление».

## Breaking / обязательные шаги

- **Breaking:** GitHub `## ⚠️ Breaking changes`; Telegram — `⚠️ Breaking changes`, пункты с `•`. Нет breaking — секцию не пиши.
- **При обновлении:** см. «Стиль» и «Миграции БД» — отдельная короткая секция в конце, только при реальных шагах для админа.

## Скриншоты к посту в Telegram

Если в релизе меняется то, что видно глазами (страница кабинета, админки,
окно), к посту прикладываются скриншоты: так сразу видно, что поменялось, и
текст можно не раздувать. Правки без видимого эффекта (бэкенд, тексты бота)
скриншотов не требуют.

**Как уходят.** `tools/release` берёт картинки из `release-screenshots/`
(корень репозитория, папка в `.gitignore`) и шлёт их альбомом в ту же тему.
Подпись к фото в Telegram режется на 1024 символах, поэтому:

- **пост до 1024 видимых символов** уходит подписью к альбому — одно сообщение,
  картинки прямо над текстом;
- **пост длиннее** уходит отдельно, а альбом — ответом на него с подписью «Как
  это выглядит в X.Y.Z».

Хочется картинки в самом посте — держи телеграм-блок коротким. Порядок в
альбоме — по имени файла (`01-…`, `02-…`), до 10 картинок, до 10 МБ каждая.
`preview` печатает, какие файлы уйдут и каким способом. Если пост ушёл
отдельно, а альбом нет — `go run ./tools/release photos <message_id>` (без
дубля поста).

**Как снимать.** Скрипт-образец — `tools/cabinet-visual-check/release-shots.mjs`:
поднимает собранный `dist` с подставным API, открывает страницу, проходит
сценарий (клики, ввод, прокрутка) и обводит изменённое место жёлтой рамкой с
подписью — функция `mark(locator, 'Подпись', side)`.

1. `cd web/cabinet && npm run build` — снимать надо то, что уходит в релиз.
2. Скопировать сценарии в скрипте под этот релиз; данные — фикстура в
   `tools/cabinet-visual-check/fixtures/` (выдуманные, без настоящих
   пользователей). Снимать **с подставными данными, а не со стенда или прода**.
3. `node tools/cabinet-visual-check/release-shots.mjs internal/cabinet/web/dist <фикстура> release-screenshots`
   (Playwright один раз: `cd tools/cabinet-visual-check && npm ci && npx playwright install chromium`).
4. **Посмотреть каждый снимок глазами** и переснять, если подпись закрывает
   текст интерфейса, рамка режет соседнюю строку или в кадре не то состояние.
   Подпись — 2–5 слов о пользе («Итог рассылки прямо в кабинете»), не название
   компонента.

Что снимать: по снимку на каждый пункт «🚀 Новое» с видимым эффектом и, если
поменялся телефон, — хотя бы один снимок 390 px. ПК — 1440 px. Обычно 3–6
снимков; десять — потолок альбома, а не цель.

Скриншоты утверждаются **вместе с текстом**: перед вопросом «публиковать?»
показать их пользователю (файлами), а не только перечислить.

## Workflow публикации (обязательно)

1. Сгенерируй / перезапиши `RELEASE_NOTES.md`. Если в релизе есть видимые
   изменения — сними скриншоты в `release-screenshots/` (раздел выше).
2. Кратко покажи в чате версию и суть, приложи скриншоты; спроси: **устраивают
   ли текст и картинки? Публиковать?**
3. **Стоп.** Пока нет явного положительного ответа (`да` / `ок` / `публикуй` / аналоги) — **не** пушь, **не** создавай release, **не** шли в Telegram.
4. После согласия:
   1. **Коммиты должны быть на `main`.** `tools/release` вызывает
      `gh release create <tag>` без `--target`, поэтому GitHub создаёт тег из
      **default branch**. Публикация с фича-ветки повесит тег 5.x на старый
      код main: релизноты будут описывать то, чего в теге нет, а образы
      `latest` и `<version>` соберутся неполными. Проверь `git log origin/main`
      и влей ветку (обычно fast-forward) до публикации.
   2. Превью: `go run ./tools/release preview`
   3. Публикация: `go run ./tools/release publish`  
      (или по отдельности `github` / `telegram`). Если телеграм упал по лимиту —
      сократи телеграм-блок и повтори только `telegram`, GitHub Release уже создан.
   4. Верни в чат URL GitHub Release и факт отправки в тему форума (пост и,
      если были, альбом скриншотов).

Конфиг: локальный **`.env.release`** (образец — `.env.release.sample`). Токен announce-бота и `RELEASE_TG_MESSAGE_THREAD_ID` (тема, напр. `31`) — только там, **никогда** в git и не в чат.

CLI лежит в `tools/release/` — **не** входит в Docker-образ магазина (`./cmd/app` only; `tools/` в `.dockerignore`).

## Активация

Релизноты, changelog, текст для канала + GitHub, перезапись `RELEASE_NOTES.md`, публикация релиза.

## Инструменты

- Редактируй **`RELEASE_NOTES.md`**; смотри `git` при подготовке содержания.
- Публикация — только **`go run ./tools/release …`** после явного «да».
