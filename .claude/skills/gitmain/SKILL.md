# Подтягивание обновлений с main

Когда основная ветка `main` движется вперёд (новые фичи, хотфиксы), текущая
ветка может отстать. Это скилл помогает синхронизироваться без ручного
разрешения конфликтов.

## Когда применять

- Ветка отстала от main на несколько коммитов, нужна синхронизация
- Перед мержем в main для уменьшения конфликтов
- Если CI упал из-за того, что код несовместим с новыми изменениями в main
- Не нужно использовать, если конфликты критичные (требуют обсуждения)

## Порядок

### 1. Проверить текущее состояние

```bash
git status
git branch
git log --oneline -5  # последние коммиты текущей ветки
```

Убедиться:
- Нет незакоммиченных изменений (всё committed или stashed)
- Текущая ветка не main (чтобы не перезаписать)

### 2. Получить актуальные обновления main

```bash
git fetch origin main
```

Смотреть разницу:

```bash
git log --oneline main..HEAD  # коммиты в текущей ветке, но не в main
git log --oneline HEAD..main  # коммиты в main, но не в текущей ветке
```

### 3. Выбрать стратегию слияния

**Rebase (рекомендуется для фич):**

```bash
git rebase origin/main
```

Плюсы:
- История линейна, без конфликтующих мержей
- Проще читать git log

Минусы:
- Если были конфликты, нужно их разрешать вручную
- Переписывает историю (не делать для публичных веток)

**Merge (безопаснее):**

```bash
git merge origin/main
```

Плюсы:
- История сохраняется полностью
- Если нет конфликтов, проходит автоматически

Минусы:
- Создаёт merge commit (шумит в истории)
- Граф коммитов становится сложнее

### 4. Разрешить конфликты (если есть)

Если конфликт:

```bash
git status  # покажет файлы с конфликтами
```

Файл с конфликтом выглядит вроде:

```
<<<<<<< HEAD
  версия в текущей ветке
=======
  версия в main
>>>>>>> origin/main
```

**Руководство по разрешению:**

1. Открыть файл в редакторе
2. Выбрать, какую версию оставить (или обе, если нужно)
3. Удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`
4. Сохранить файл

Пример разрешения:

```javascript
// До:
<<<<<<< HEAD
const API_URL = 'http://localhost:3000'
=======
const API_URL = process.env.VITE_API_URL || 'https://api.example.com'
>>>>>>> origin/main

// После (если нужна конфиг из переменной):
const API_URL = process.env.VITE_API_URL || 'http://localhost:3000'
```

После разрешения:

```bash
git add файл_с_конфликтом
git rebase --continue  # или git merge --continue если был merge
```

### 5. Проверить результат

```bash
git log --oneline -10  # убедиться, что история выглядит правильно
git status  # всё ли committed?
cd web/cabinet && npm run typecheck && cd -  # если фронтенд
go test -race ./... && golangci-lint run  # если бэкенд (полный набор — skill go-backend-test-runner)
```

### 6. Если что-то пошло не так

Откатить:

```bash
# Если rebase:
git rebase --abort

# Если merge:
git merge --abort
```

Или вернуться на сохранённое состояние:

```bash
git reflog
git reset --hard HEAD@{N}  # где N — номер нужного состояния
```

### 7. После успешного слияния

```bash
# Если был rebase, нужно force-push (только если ветка ещё не в PR!)
git push origin -f

# Если был merge, обычный push
git push origin
```

## Контрольный список

- [ ] `git status` показывает clean рабочую директорию
- [ ] Нет незакоммиченных изменений
- [ ] Выбрана правильная стратегия (rebase или merge)
- [ ] Конфликты разрешены правильно
- [ ] Tests прошли после слияния
- [ ] Git log выглядит разумно (нет странных коммитов)
- [ ] Push прошёл (если нужно)

## Notes

- Если ветка уже в PR на GitHub, **force-push может перезаписать PR**. Лучше
  попросить review перед тем, как пулить main.
- Если main часто меняется, лучше мержить чаще (каждый день) вместо редких
  больших слияний.
- Всегда тестируйте после слияния, даже если конфликтов не было.
