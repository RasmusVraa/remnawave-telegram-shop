# Обновление

На сервере в каталоге проекта:

```bash
git pull
docker compose pull
docker compose down && docker compose up -d
```

Миграции БД применяются сами при старте нового образа.

**Тексты бота берутся с диска.** В `docker-compose.yaml` папка `./translations` смонтирована в контейнер, поэтому бот читает `translations/*.json` из каталога проекта, а не из образа. Новые ключи появляются там только после обновления клона (`git pull` выше; свои правки текстов сохраните заранее). Иначе вместо нового текста бот покажет имя ключа.

После смены переменных в `.env` пересоздайте контейнер:

```bash
docker compose up -d --force-recreate
```

## Переход на Remnawave 3.x (бот 5.0.0)

> **Ломающее обновление.** Панель и бот обновляются вместе: бот `4.x` не работает
> с панелью `3.x`, бот `5.x` не работает с панелью `2.8`. Подробности —
> [compatibility.md](./compatibility.md).

Порядок:

1. **Снимите дамп БД бота** и убедитесь, что он восстанавливается в пустую базу.
   Непроверенный дамп не считается бэкапом.
2. Зафиксируйте текущий рабочий образ бота **по digest**, а не по тегу `latest`, —
   иначе откат вернёт не то, что было.
3. Обновите панель до `3.3.*` или новее (поддерживается по `3.4.*` включительно):
   - в её compose-файле смените образ `remnawave/backend:2` на `remnawave/backend:3`;
   - в `.env` переименуйте `JWT_AUTH_SECRET` в `APP_SECRET` (значение переносится как есть);
   - удалите `JWT_API_TOKENS_SECRET`, `SWAGGER_PATH`, `SCALAR_PATH`, `IS_DOCS_ENABLED`;
   - примените: `docker compose pull remnawave && docker compose down && docker compose up -d`.

   Инструменты панели переехали на фиксированные адреса: Swagger — `/api/backend-tools/swagger`,
   Scalar — `/api/backend-tools/scalar`, очереди — `/api/backend-tools/queues`.
   Права существующих API-токенов панель мигрирует автоматически.
4. Ноды обновлять не требуется: панель `3.3` совместима со старыми нодами.
   Обратной совместимости нет — нода `3.3` требует панель `3.3+`, поэтому порядок
   всегда «сначала панель, потом ноды». Отдельной настройки ноды не требуют;
   обновление до `3.3` нужно только ради функции Geocheck.
5. Обновите бота — миграции БД применятся при старте.
6. Проверьте по горячим следам: покупка, продление, устройства, карточка пользователя в админке.

Между шагами 3 и 5 бот не работает: старый код не умеет находить пользователей в новой
панели. Окно простоя стоит сделать коротким и объявленным.

## Обновление панели 3.3.\* → 3.4.\*

Бота обновлять не нужно и простоя нет: `3.4.0` не тронул ни один эндпоинт, к которому
обращается бот. Ломающая правка API — только в объекте хоста (`excludedInternalSquads` →
`internalSquads` с `mode` и `squads`), а бот к `/api/hosts` не обращается.
Разбор — [compatibility.md](./compatibility.md#remnawave-340).

Единственное, что стоит проверить **после** обновления панели: доступ к хостам теперь
выдаётся по internal squads, а не отбирается у них. Панель мигрирует старые правила сама,
но если какой-то хост окажется во включающем режиме с неполным списком сквадов, клиенты
на этих сквадах потеряют серверы в подписке — тихо, без ошибок в логах бота. Откройте
хосты в панели и сверьте их сквады с теми, что бот выдаёт при покупке.

### Откат

Миграция бота `000041` **строго аддитивная** — только добавляет колонки
`remnawave_user_id` и `remnawave_short_uuid`, ничего не переписывая. Запросы к БД
используют явный список колонок, поэтому предыдущая версия бота работает с новой схемой
и не видит лишних полей.

Практически это значит: **откат = вернуть предыдущий образ, БД трогать не нужно.**
Восстановление из дампа — аварийный сценарий, а не штатный путь. Но откатывать
придётся вместе с панелью.

### Что изменилось внутри

- Клиент панели переведён с `uuid` на числовой `id`; удалённый `by-telegram-id`
  заменён на `GET /api/users/stream` с фильтрами.
- В таблицу `customer` добавлены `remnawave_user_id` и `remnawave_short_uuid`.
  Заполняются **лениво** — при первом обращении к клиенту, отдельный скрипт не нужен.
  Схема самовосстанавливается: если запись оказалась неверной, следующий резолв её исправит.
- Продление подписки считает панель (`POST /api/users/{userId}/actions/extend`),
  что убирает гонку, когда бот и кабинет продлевают одного клиента одновременно.
