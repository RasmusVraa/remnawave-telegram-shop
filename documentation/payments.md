# Платежи, вебхуки и проверка статуса

## Поддерживаемые способы оплаты

| Система | Переключатель | Примечание |
|---------|---------------|------------|
| [YooKassa](https://yookassa.ru/developers/api) | `YOOKASA_ENABLED` | Карты / привычные методы YooKassa |
| [Platega](https://platega.io) | `PLATEGA_ENABLED` | Общая форма, СБП, эквайринг, международные карты, крипта |
| [CryptoPay](https://help.crypt.bot/crypto-pay-api) | `CRYPTO_PAY_ENABLED` | Крипто через Crypto Bot |
| [Heleket](https://heleket.com) | `HELEKET_ENABLED` | Крипто; в интерфейсе называется «Другая крипта» |
| Telegram Stars | `TELEGRAM_STARS_ENABLED` | Оплата звёздами в Telegram |

Переменные — в [env.md](./env.md) (разделы оплат). Ключи и реквизиты задаются только в `.env`; включать и выключать уже настроенные способы можно без рестарта — в web-админке «Настройки бота» → «Способы оплаты».

## ЮKassa: кнопки по способам

По умолчанию у ЮKassa одна кнопка — форма со всеми способами. `YOOKASA_PAYMENT_METHODS` превращает её в несколько кнопок в боте и кабинете, по одной на способ, в заданном порядке:

```env
YOOKASA_PAYMENT_METHODS=sbp,bank_card,all
```

Доступно: `all` (форма со всеми способами), `sbp`, `bank_card`, `sberbank`, `tinkoff_bank`, `yoo_money`. Кнопка конкретного способа сразу открывает его на форме ЮKassa, но сменить способ там уже нельзя. Каждый способ должен быть подключён в личном кабинете ЮKassa. Настройка меняется и в админке.

На странице оплаты кабинета заранее выбран способ, которым человек платил в прошлый раз; тем, кто ещё не платил, — `CABINET_CHECKOUT_DEFAULT_METHOD` (например `yookassa:sbp` или `platega_sbp`).

Тексты кнопок — ключи `yookasa_<способ>_button` в `translations/ru.json` / `en.json`. Если в ваших файлах переводов этих ключей ещё нет, бот подставит встроенные подписи («⚡ СБП», «💳 Банковская карта» и т.д.).

## HTTP-сервер бота

Порт задаётся `HEALTH_CHECK_PORT`. На нём же:

- `/healthcheck` — статус БД, Remnawave, версия сборки;
- при включённом кабинете — `/cabinet/*` и `/cabinet/api/*`;
- вебхуки оплат (если заданы пути в env);
- вебхук панели Remnawave (`REMNAWAVE_WEBHOOK_PATH`, см. [notifications.md](./notifications.md)).

Рекомендуется слушать порт локально (`127.0.0.1`) и пускать наружу только через reverse proxy. Пример — [reverse-proxy.md](./reverse-proxy.md).

## Вебхуки и поллинг (YooKassa / Platega)

В `YOOKASA_WEBHOOK_URL` и `PLATEGA_WEBHOOK_URL` указывайте **только путь** (суффикс), без домена — например `/yookassa-hook`.

| Значение | Поведение |
|----------|-----------|
| **Пусто** | Успешные оплаты подтверждаются **поллингом** (бот сам спрашивает статус у API по расписанию) |
| **Путь задан** | Платёжка может слать уведомление на `https://ваш-домен` + путь (через reverse proxy) |

**CryptoPay** в этом форке подтверждается поллингом.  

## Прокси для ЮKassa

Если сервер расположен там, откуда `api.yookassa.ru` доступен нестабильно, платежи
падают с `500` в кабинете, а в логах видно:

```
failed to send request: Post "https://api.yookassa.ru/v3/payments": net/http: TLS handshake timeout
```

Характерный признак — отказы **плавающие**: часть запросов проходит, часть отваливается
по таймауту. Проверить можно так (десять подряд `401` = путь чистый, `000` = потери):

```bash
for i in $(seq 1 10); do curl -s -o /dev/null -w '%{http_code}
' --max-time 8 https://api.yookassa.ru/v3/payments; done
```

Лечится переменной `YOOKASA_PROXY_URL`:

```env
YOOKASA_PROXY_URL=socks5://user:pass@host:1080
```

Поддерживаются `http://`, `https://` и `socks5://`, авторизация — в самом URL.
Пусто (по умолчанию) — прямое соединение, поведение не меняется.

> **Не используйте вместо этого глобальный `HTTPS_PROXY`.** Он уведёт в прокси и
> обращения бота к панели Remnawave по внутреннему адресу docker-сети, которые
> снаружи не резолвятся, — сломается вся работа с панелью. `YOOKASA_PROXY_URL`
> применяется только к запросам ЮKassa.

Клиент ЮKassa работает с таймаутом 30 секунд, поэтому зависший прокси не удерживает
HTTP-обработчик кабинета бесконечно.

## Platega: кнопки

При `PLATEGA_ENABLED=true` обязательны `PLATEGA_MERCHANT_ID` и `PLATEGA_SECRET`.

Кнопки задаёт `PLATEGA_PAYMENT_METHODS` (в админке: Платежи → Platega: кнопки), порядок — как в списке:

- `all` — общая форма: платёж создаётся без `paymentMethod` через `/v2/transaction/process`, способ плательщик выбирает на странице Platega. Это значение по умолчанию.
- `sbp`, `acquiring` (карты), `worldwide` (международные карты), `crypto` — отдельная кнопка, платёж создаётся с кодом способа (2, 11, 12, 13), плательщик сразу попадает на нужный способ.

Способы кроме `all` должны быть включены в кабинете Platega, иначе платёж не создастся. Прежние флаги `PLATEGA_SBP_ENABLED`, `PLATEGA_CARDS_ENABLED`, `PLATEGA_ACQUIRING_ENABLED`, `PLATEGA_WORLDWIDE_ENABLED`, `PLATEGA_CRYPTO_ENABLED` больше не читаются. Способа «Карта МИР» (код 10) в Platega больше нет, новые счета по нему не создаются; старые остаются в истории.

## Heleket: «Другая крипта»

Счёт выставляется в рублях (`HELEKET_CURRENCY`, по умолчанию `RUB`), конкретную монету и
сеть выбирает плательщик на странице Heleket. `order_id` счёта — это `HELEKET_ORDER_PREFIX`
плюс id покупки (`shop-42`): по нему вебхук находит покупку обратно, и он же делает
повторный запрос идемпотентным.

Префикс — не украшение. `order_id` уникален в пределах мерчанта, поэтому без него счёт
тестового стенда может быть зачтён боевому (и наоборот), а после восстановления БД из
бэкапа переиспользованный id покупки подтянул бы чужой старый счёт со старой суммой.
Стенды на одном мерчанте обязаны иметь разные префиксы.

Отличия от остальных касс, о которых стоит знать:

- **Адрес колбэка не хранится в ЛК Heleket** — он уходит в каждом счёте, поэтому в
  `HELEKET_WEBHOOK_URL` удобнее указать полный URL. Путь для mux вычисляется из него.
- **Поллинг не выключается вебхуком.** У остальных касс это «или/или», здесь — «и то, и
  другое»: крипта необратима, и пропущенный колбэк означал бы, что человек заплатил и
  ничего не получил. С вебхуком поллинг ходит раз в минуту, без него — раз в 5 секунд.
- **Тело вебхука ничего не зачисляет.** Статус всегда перезапрашивается через
  `/v1/payment/info`. Но перезапрос подтверждает только сам статус, а не то, к какой
  покупке платёж относится, — поэтому подпись колбэка **блокирующая**: неподписанное
  тело получает 403 и до обращения к Heleket не доходит. Id покупки берётся строго из
  подтверждённого кассой `order_id`, никогда из тела запроса. Перед зачислением
  дополнительно сверяются `uuid`, сумма и валюта платежа с покупкой; расхождение —
  повод позвать админа, а не зачислить.
- **Оплата на закрытый счёт не зачисляется автоматически.** Если деньги пришли на
  отменённый/истёкший счёт или Heleket заморозил платёж AML-проверкой (`locked`), бот
  пишет в группу платежей и ждёт ручного решения — вместо того чтобы гадать и рисковать
  задвоить активацию.
- **Обработка одной покупки сериализуется.** Вебхук и поллинг работают параллельно, и
  без блокировки оба могли бы одновременно провести «прочитали pending → активировали
  подписку → записали paid» и продлить подписку дважды. Статус перечитывается из БД
  под блокировкой, а не берётся снимком, с которым поллер начинал обход.
- **Незакрытые счета самоочищаются.** Поллер берёт покупки в `pending` и `new`,
  самыми старыми вперёд и порцией не больше 200 — иначе разросшийся хвост
  брошенных счетов съедал бы весь бюджет прохода и упирался бы в рейт-лимит
  кассы. Счёт, переживший свой `lifetime`, закрывается, даже если Heleket всё
  ещё держит его в нетерминальном статусе: сам оттуда он уже не выйдет.
- **Покупки в `new` подбираются.** Если создание счёта прошло, а запись
  `heleket_id` в базу упала, покупка осталась бы в `new` навсегда. Поллер
  находит такой счёт по `order_id`, дописывает `heleket_id`/`heleket_url`
  обратно и дальше ведёт его как обычный.
- **Отмена по «нет такого счёта» — только для протухших.** Heleket отвечает на
  несуществующий счёт `422 {"message":"Payment not found"}`. Сообщение сверяется целиком:
  поиск подстроки «not found» ловил бы и `Merchant not found` при опечатке в merchant id,
  и 404-страницу CDN — то есть одна ошибка конфигурации отменила бы все живые счета.
  Вдобавок покупка отменяется, только когда её счёт уже пережил свой `lifetime`.
- **Чеки в «Мой налог» не отправляются.** Heleket отсутствует в белом списке
  `invoiceUsesMoynalogReceipt`, `MOYNALOG_RECEIPT_FOR` на него не влияет.

## «Мой налог»

После успешной оплаты можно отправлять доход в API «Мой налог» (`MOYNALOG_*`).  
Чек сначала сохраняется в БД, а если ФНС недоступна — переотправляется по расписанию `MOYNALOG_RETRY_CRON` в течение `MOYNALOG_RETRY_MAX_AGE_HOURS` от времени оплаты; дата дохода в чеке — дата оплаты, а не отправки. Подробнее — [env.md](./env.md#мой-налог).  
Если сервер вне РФ — см. [moynalog-proxy.md](./moynalog-proxy.md).
